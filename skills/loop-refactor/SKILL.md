# 리팩터링 계획

리팩터링의 실행은 `loop` 스킬이 한다. 행동을 지키는 조각(`kind: keep`)의 묶음이고, 조각 검사가 조각마다 행동이 그대로인지 확인한다.
이 스킬은 그 앞 단계다. 무엇을 고칠지 찾고, 목표 모양을 사용자와 정하고, 조각 초안과 이슈로 만든다.
규칙의 정본은 `loop` 스킬의 "증명 계약"과 "모양 규칙"이다. 아래 `$L`은 `${CLAUDE_PLUGIN_ROOT}/scripts`다.

## 1. 고칠 곳 찾기

```bash
python -I "$L/shape.py" audit            # 프로젝트 전체에 모양 규칙을 건다. 규칙별 목록
python -I "$L/shape.py" audit --json     # 조각으로 묶을 때 읽는다
```

기계가 내는 목록이 출발점이다. LLM으로 코드를 훑어 고칠 곳을 찾지 않는다.
`config.shape`가 없으면 먼저 `roots`를 넣는다(`loop-init` 스킬). 목록에 없지만 사용자가 지목한 것(같은 것의 변형인데 상속 없이 반복되는 코드 등)은 따로 받는다.

## 2. 목표 모양 정하기

사용자가 정한다. 초안을 만들어 보여 주고 승인을 받는다.

- **폴더**: 지금 트리와 목표 트리를 나란히 보인다. 위는 영역, 그 아래는 역할, 깊이 3단 이하다. 폴더 이름 목록을 정해 `config.shape.folder_names`에 넣는다.
  채워진 정도보다 "어디 있을지 이름으로 안다"가 우선이다. 파일이 하나뿐인 폴더도 이름이 맞으면 둔다.
- **타입 모음**: 여러 곳이 쓰는 enum·struct를 영역마다 어느 파일에 모을지 정한다(예: `Types/PartTypes.cs`).
- **남길 예외**: 목록 중 일부러 남길 것과 이유를 정한다. 구현이 하나뿐인 인터페이스가 외부 경계(네트워크·파일·시간)인 경우가 그렇다. 조각의 `allow`에 들어간다.

## 3. 테스트 가르기

고칠 타입을 참조하는 테스트 파일만 읽는다. 저장소 `CLAUDE.md`의 테스트 규칙으로 둘로 가른다.

- **지킴이**: 공개된 입구로 행동을 확인하는 테스트. 조각의 `guards`가 된다. 리팩터링 뒤에도 고치지 않은 채 통과해야 한다.
- **물러날 테스트**: 없애거나 합칠 구조(클래스·필드·호출 순서)를 검사하는 테스트. 조각의 `retire`에 이유와 함께 들어간다.
  물러나면 spec이 요구하는 행동을 확인하는 테스트가 사라지는 경우, 공개된 입구로 확인하는 대체 테스트를 같은 조각에 넣는다.

지킴이가 하나도 없는 영역은 리팩터링 전에 행동 테스트를 먼저 쓰는 조각을 앞에 둔다(`kind: change`가 아니다. 이미 있는 행동을 확인하는 테스트라 구현 전에도 통과한다. `keep` 조각에 새 테스트로 넣는다).

## 4. 조각으로 묶기

조각 하나는 혼자 검증할 수 있는 이동 하나다. 조각마다 `kind: keep`, `files`(새 파일 포함), `guards`, `retire`, `allow`, `acceptance`를 적는다.
수용 기준은 기계가 확인할 수 있게 쓴다. "audit에서 이 대상들이 사라진다", "지킴이가 고치지 않고 통과한다" 같은 문장이다.

순서는 안쪽에서 바깥쪽으로 간다.

1. 타입 모으기: 타입 하나만을 위한 파일을 타입 모음 파일이나 쓰는 클래스 파일로 합친다.
2. 미리 만든 추상화 걷어내기: 구현이 하나뿐인 인터페이스, 자식이 하나뿐인 베이스, 쓰이지 않는 `virtual`을 없앤다.
3. 변형을 상속으로 모으기: 같은 것의 변형이 반복되는 곳에 베이스 클래스를 둔다.
4. 닫기와 이름: `sealed`, `…Base`.
5. 폴더 옮기기: 맨 마지막에 한다. 경로가 바뀌면 앞 조각들의 `files`가 어긋난다.

한 조각이 너무 많은 파일을 건드리면 영역별로 나눈다. 폴더 옮기기는 영역 하나에 조각 하나다.

## 5. 이슈로 만들기

사용자 승인을 받고 한다(외부 서비스 쓰기). 마일스톤 하나를 만들고, 목표 모양과 대상 목록을 담은 이슈를 `ready-for-agent`로 연다.
조각 초안은 이슈 본문에 적는다. 그 뒤는 `loop` 스킬의 고르기부터 평소대로 돈다. 설계 세션이 초안을 조각 목록으로 확정한다.

## 6. 끝 확인

루프가 끝나면 `shape.py audit`의 건수가 남기기로 한 예외만 남았는지, `shape.py report --base origin/<기준 브랜치>`의 숫자가 줄어든 쪽인지 사용자에게 보인다.

## Unity에서 조심할 것

- 파일을 옮기거나 이름을 바꿀 때 `.meta`를 함께 옮긴다. GUID가 바뀌면 그 에셋을 가리키던 참조가 끊긴다(조각 검사가 막는다).
- MonoBehaviour·ScriptableObject는 파일 이름과 클래스 이름이 같아야 하고 파일 하나에 하나다. 다른 파일에 합치지 않는다.
- 타입 이름과 네임스페이스는 바꾸지 않는 것이 기본이다. 바꾸면 UXML의 사용자 정의 요소 이름, `[SerializeReference]`로 저장된 타입, 문자열로 적힌 타입 이름이 끊길 수 있다.
  바꿔야 하면 그 조각의 수용 기준에 끊길 수 있는 곳의 확인을 넣는다.
- 직렬화 필드의 이름을 바꾸면 저장된 값이 사라진다. `[FormerlySerializedAs]`를 붙인다.
- asmdef 경계를 넘는 이동은 참조 방향을 바꾼다. 영역을 옮기기 전에 asmdef 참조가 한 방향으로 남는지 본다.

## 하지 않는 것

- 행동을 바꾸지 않는다. 리팩터링 중에 제품 동작을 바꿔야 하는 것이 나오면 그 조각은 빼고 사용자에게 알린다.
- 옛 코드 전체를 한 번에 맞추려 하지 않는다. 영역을 골라 한 루프에 하나씩 한다.
