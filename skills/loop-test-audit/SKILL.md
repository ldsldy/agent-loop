# 테스트 점검

테스트는 spec이 정한 행동을 지키는 수단이다. 지금 코드의 모양을 붙잡아 두는 제약이 아니다. 권한은 spec, 구현, 테스트 순이다(저장소 `CLAUDE.md`의 테스트 규칙이 정본).
이 스킬은 그 기준으로 테스트를 가끔 점검한다. 코드를 고치지 않는다. 결과는 사용자에게 보이고, 고치는 일은 `loop-refactor`와 `loop` 스킬로 넘긴다.
아래 `$L`은 `${CLAUDE_PLUGIN_ROOT}/scripts`다.

## 1. 기계 점검

```bash
python -I "$L/audit_tests.py"            # 후보 목록
python -I "$L/audit_tests.py" --json
```

토큰이 들지 않는다. 내는 것은 후보이고 판정이 아니다.

| 목록 | 뜻 | 흔한 오탐 |
| --- | --- | --- |
| 테스트만 쓰는 타입 | 테스트 아닌 코드 어디서도 쓰지 않는데 테스트가 참조하는 타입. 테스트 때문에 남은 구조일 수 있다 | Unity가 에셋이나 빌드 단계에서 부르는 타입(빌드 스크립트, 에셋에 연결된 ScriptableObject) |
| 테스트 가짜를 위한 인터페이스 | 실제 구현은 하나뿐이고 나머지 구현이 테스트 안에 있다 | 외부 경계(네트워크·파일·시간)의 인터페이스는 남긴다 |
| 안을 들여다보는 테스트 | 리플렉션으로 비공개 멤버를 읽는다. 내부가 바뀌면 깨진다 | 공개된 입구가 정말 없는 Unity 내부 상태 |
| 확인하는 것이 없는 테스트 | 단언도, 단언하는 도우미 호출도 없다 | 예외가 안 나는 것 자체가 확인인 테스트 |
| 꺼 둔 테스트 | `[Ignore]`·`[Explicit]` | |

## 2. spec과 대조

영역 하나씩 한다. 한 번에 프로젝트 전체를 읽지 않는다.

1. 그 영역의 spec 이슈(`spec` 라벨) 본문에서 요구하는 행동을 뽑는다.
2. 그 영역 테스트의 이름 목록을 읽는다(fixture와 메서드 이름). 본문은 이름으로 판단이 안 서는 것과 1단계의 후보만 연다.
3. 테스트마다 셋 중 하나로 가른다.
   - **행동**: spec의 어느 요구를 공개된 입구로 확인한다. 지킴이다.
   - **구조**: 클래스·필드·호출 순서처럼 바꿀 수 있는 내부를 검사한다. 물러날 후보다. 그 테스트가 사라지면 확인이 없어지는 spec 요구가 있는지 함께 적는다.
   - **모름**: spec에서 근거를 찾지 못했다. 사용자에게 묻는다. 추측으로 가르지 않는다.
4. spec이 요구하는데 확인하는 테스트가 없는 행동을 적는다.

## 3. 묶인 구조 찾기

1단계의 "테스트만 쓰는 타입"과 "테스트 가짜를 위한 인터페이스"를 하나씩 본다.

- 테스트와 함께 지울 수 있는가. 그 타입이 있어야만 통과하는 테스트가 2단계에서 "구조"로 갈렸으면 함께 물린다.
- 남겨야 하는가. Unity가 부르는 진입점이거나 외부 경계면 남기고 이유를 적는다.
- 테스트를 통과시키려고 남겨 둔 분기·매개변수·공개 범위(`internal`을 `public`으로 넓힌 것, `InternalsVisibleTo`)도 같은 눈으로 본다.

## 4. 결과

사용자에게 네 목록으로 보인다. 영역, 대상, 근거(spec 이슈 번호나 파일과 줄)를 붙인다.

| 목록 | 다음에 가는 곳 |
| --- | --- |
| 지킴이(행동을 확인하는 테스트) | 정리 루프 조각의 `guards` |
| 물러날 테스트와 이유 | 정리 루프 조각의 `retire` |
| 테스트에 묶인 구조 | `loop-refactor` 스킬의 고칠 곳 목록에 더한다 |
| 빈 곳(spec 요구인데 테스트 없음) | 이슈로 만든다. 사용자 승인을 받는다 |

테스트를 지우거나 고치는 일은 여기서 하지 않는다. 조각의 `retire`에 적혀 조각 검사를 거쳐야 한다(`loop` 스킬 "증명 계약").

## 하지 않는 것

- 통과율이나 커버리지를 올리려는 점검이 아니다. 테스트 수를 줄이는 것도 목표가 아니다.
- spec에 근거가 없다는 이유만으로 테스트를 물리지 않는다. 모르면 묻는다.
